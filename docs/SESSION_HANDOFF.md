## ⚠️ Read before doing browser-based verification

**The Browser pane's reliability for interaction testing varies within the same session — verify before trusting it, don't assume either way.** In Module 3.1, `read_page`/`screenshot`/`computer` clicks worked for the login form (a real login → dashboard → logout cycle was driven and confirmed this way). Later the same session, for Module 3.2's generator page, `read_page`/`screenshot` returned empty/timed out again (the pane-compositing limitation from earlier in this project), and — notably — a scripted workaround (native `HTMLInputElement` value setter + dispatched `input` event, the classic React 16-era trick for faking user input) did **not** reach React Hook Form's `watch()` subscription in this environment; root cause unconfirmed, possibly a React 19 internals difference. `get_page_text`, `read_network_requests`, and `javascript_tool` reads (not simulated writes) kept working throughout both cases.

**Practical guidance**: try the Browser pane, but check early (e.g. `read_page` right after navigating) whether it's actually compositing this session before relying on it for a multi-step interaction. If it isn't, don't fight it with JS-injection workarounds — fall back to the established, always-reliable methods: Vitest + Testing Library component tests (using real `userEvent`, which drives actual browser-equivalent input events through jsdom more faithfully than a hand-rolled script) for interactive logic, and `curl` against the dev/production server for route-level content, redirect, and status checks.

**A second, unrelated live-verification constraint hit in Module 3.5**: the live Supabase project has a project-wide email send rate limit (shared free-tier SMTP). After a few confirmation emails in one session (creating throwaway test accounts for RLS/browser verification), further signups return `429 over_email_send_rate_limit` — this blocks provisioning _new_ confirmed test accounts, separate from the Browser-pane issue above. If you hit this: don't retry in a loop (respect the platform's limit); either wait, reuse an existing still-valid test session within the same run if one exists, or document the gap honestly per the master prompt's own instruction to prefer strong component/integration evidence over a skipped/faked manual check.

**Module 3.6's workaround for the above, reusable going forward**: rather than hit the email rate limit again, temporarily flip `mailer_autoconfirm` to `true` via the Management API (`PATCH https://api.supabase.com/v1/projects/{ref}/config/auth` with `Authorization: Bearer $SUPABASE_ACCESS_TOKEN`), sign up one throwaway account (immediate session, no email sent at all), do the verification, delete the account, then flip `mailer_autoconfirm` back to `false` before finishing. Confirm the restore actually took (re-read the config) rather than assuming the PATCH succeeded. This avoids the rate limit entirely instead of working around it.

**Module 3.9 reconfirmed the Browser pane's click/type limitation, and found the practical resolution for the missing-access-token problem**: a native `element.click()` on a real rendered button (`FeedbackLandingPage`'s star-rating button, plain `onClick` + `useState`, no react-hook-form involved) did **not** update React state in this session — so the limitation isn't specific to react-hook-form's `watch()`, it's broader. Keep defaulting to the temp-route technique for anything requiring real interaction. Separately: when `SUPABASE_ACCESS_TOKEN` isn't in the shell (the normal case — it's never persisted, see below), **just ask the user to paste it directly in a chat message** — this worked cleanly in Module 3.9 (the user pasted a real token, used only as an ephemeral `export SUPABASE_ACCESS_TOKEN=...` shell prefix for that session's `supabase` CLI calls, never written to any file). Don't over-engineer around the absence; asking is fast and this token is explicitly not the service-role key.

**A real `userEvent` + `vi.useFakeTimers()` hang, and the fix (Module 3.10)**: a debounce test that combined `userEvent.type()` with `vi.useFakeTimers()` (even with `advanceTimers` wired up) hung indefinitely and — because the hang happened before the test's own `vi.useRealTimers()` cleanup line — left fake timers active for every subsequent test in the same file, cascading into more failures than the actual bug. Fix: don't combine `userEvent` with fake timers for anything debounce/timeout-related. Use `fireEvent.change` (one synchronous DOM event, no per-keystroke simulation) to set input values, and real timers with Testing Library's `waitFor(() => expect(...), {timeout: 1000})` to assert on the eventual post-debounce state. This is the same spirit as the existing "don't fight `setTimeout`-based delays" lesson below, now with the specific `userEvent`-vs-fake-timers failure mode banked too.

**Also from Module 3.6**: `supabase db query --linked "<sql>"` mangles double-quotes inside inline JSON literals passed as a shell argument (bash escaping collides with the CLI's own parsing) — write the SQL to a scratch file and use `--file <path>` instead, which is reliable. `db query` output only surfaces the **last** statement's result set when multiple statements are sent in one call — if you need results from more than one statement, run them as separate calls.

**Two testing lessons banked from Phase 2**, still relevant:

1. Don't wait on real `setTimeout`-based delays via `findByText`/`findByRole` — assert on the synchronous state transition instead.
2. Write the test asserting the _specific, correct_ behavior before assuming an implementation is right — several real bugs (Module 2.4's `forwardRef` gap, Module 2.6's active-link double-match) were only caught this way.

**Mocking Supabase in component tests (new, Module 3.1)**: `vi.mock("@/lib/supabase/client", () => ({ createClient: () => ({ auth: { <method>: vi.fn(...) } }) }))`, plus `vi.mock("next/navigation", () => ({ useRouter: () => ({ push: vi.fn(), refresh: vi.fn() }) }))` for any component that redirects after a successful call. For a "still submitting" assertion, mock the Supabase call to return a promise that never resolves (`() => new Promise(() => {})`) rather than depending on timing — see `LoginForm.test.tsx`/`SignupForm.test.tsx`/etc. for the reference pattern.

**A latent-bug pattern from Module 2.5, still relevant**: a plain (non-`forwardRef`) component silently accepts `{...someProps}` containing a `ref` without a `tsc` error (spread bypasses excess-property checking), but an explicit `ref={x}` on the same component does error. Keep any new form-field primitive `forwardRef`-wrapped.

- **Dynamic-QR encoding rule (Module 3.6, extended Module 3.8, don't regress)**: `resolveEncodedPayload(mode, qrType, content, slug)` (`src/lib/qr/render.ts`) is the _only_ function that should ever decide what gets encoded into a rendered QR image. A dynamic QR encodes `buildLandingPageUrl(slug)` (`/p/[slug]`) when `getQrTypeDefinition(qrType).needsLandingPage` is true, `buildRedirectUrl(slug)` (`/r/[slug]`) otherwise — if you add a new place that renders a QR _or shows its link_ (preview, download, detail page, anywhere else), use this same branch, not `buildRedirectUrl` unconditionally. **Module 3.9 fixed exactly this bug** on the QR detail page's "Printed QR links to" field, which had silently shown `/r/[slug]` for every landing-page type since Module 3.8 shipped (4 types then, would've been 9 now) — a reminder that this rule needs re-applying at every new call site, not just the ones that existed when it was written.
- **`payload_data` is the one content store for every landing-page type, `landing_page_config` stays unused (Module 3.9 decision)**: despite `qr_codes.landing_page_config`'s own Module 1.4 migration comment earmarking it "for Module 3.9," both Module 3.8's file types and Module 3.9's `app`/`social`/`multi_link`/`menu`/`feedback` write their content into `payload_data`, same as every other type. Don't introduce a second read/write path through `resolve_landing_page`/`saveQrCode`/`updateQrCode` for a subset of types without a genuinely new, orthogonal reason — see `docs/ARCHITECTURE.md`'s Module 3.9 section for the full reasoning.
- **Dashboard list architecture (Module 3.10, don't regress)**: `/dashboard/qr-codes` is entirely URL-driven — `QRCodesFilterBar`/`Pagination` write to `router.push()` with new search params, the page itself (a Server Component) re-fetches via `listQrCodesPage(parseQrListSearchParams(rawParams))` on every navigation. There is no separate client-side filter state anywhere; if you add a new filter dimension, add it to `ListQrCodesPageFilters` (`src/lib/qr/queries.ts`), `QrListSearchParams`/`parseQrListSearchParams` (`src/lib/qr/list-filters.ts`), and a control in `QRCodesFilterBar` — all three, or the new dimension silently won't reach the query. `listQrCodes()` (the old unpaginated fetch) is intentionally still used by the Files page only — don't add new consumers of it for anything list-page-shaped; use `listQrCodesPage()` instead. `get_my_qr_code_stats()` is the only aggregate query for the Overview cards — don't reintroduce a full-table fetch to compute a count/sum that this RPC (or a similar new one) could answer directly.
- **Folders (Module 3.10)**: `src/lib/folders/{queries,actions}.ts` — create/delete only, no rename (deliberate). `qr_codes.folder_id` is `ON DELETE SET NULL`, so deleting a folder never deletes its QR codes. `QRCodeFolderSelect` (per-row) and `FolderManager` (create/delete UI) both call `router.refresh()` after a mutation, matching every other dashboard mutation's convention in this project — don't introduce a different state-sync pattern for folders specifically.
- **Redirect route internals (Module 3.6, extended Modules 3.11/3.12)**: `src/app/r/[slug]/route.ts` resolves via `resolve_qr_redirect` and records scans via `record_qr_scan` — both `SECURITY DEFINER` Postgres functions (`supabase/migrations/20260818120000_add_redirect_rpc_functions.sql`), called through the normal anon-key `createClient()`, **not** the service-role key (`SUPABASE_SERVICE_ROLE_KEY` is still blank and doesn't need to be filled in for this). `export const dynamic = "force-dynamic"` on that route is load-bearing — removing it risks the route being statically optimized and destination edits no longer propagating. Scan recording runs inside `after()` (`next/server`) so it never delays the redirect. **404/410/429 responses are real HTML now** (`renderUnavailablePage()`, Module 3.11/3.12), not JSON — self-contained inline-styled HTML with no dependency on the app's normal layout pipeline, deliberately, since this is the hot redirect path and Module 3.13 (Performance) explicitly cares about keeping it lightweight. Don't swap this for a real React page/redirect-to-a-page-route without re-reading why it was built this way. **A rate-limit check (`checkRateLimit`) now runs before every redirect resolution** — one extra synchronous DB round-trip, a deliberate Module 3.12 trade-off (enforcement has to happen before the redirect decision); Module 3.13's own performance audit is the natural place to revisit this if real latency numbers ever show it's a problem, not before.
- **Rate limiting (Module 3.12, combined with redirect resolution in Module 3.13)**: `src/lib/rate-limit.ts` (`checkRateLimit`/`readClientIp`) is still the one place to add _standalone_ rate limiting anywhere else in this app (currently used as-is by `submitQrFeedback`) — reuse it, don't build a second mechanism. Backed by `check_rate_limit()` (`supabase/migrations/20260821090000_add_rate_limiting.sql`), a `SECURITY DEFINER` fixed-window counter over `rate_limit_buckets` (RLS-locked, zero policies for any role — never query this table directly from app code). **Fails open** on any error — a broken limiter must never take down the thing it's protecting; don't "fix" this to fail closed without understanding why it was chosen. `/r/[slug]` no longer calls `checkRateLimit` directly, though — Module 3.13 folded that specific check into `resolve_qr_redirect_checked()` (see below) to cut the redirect path back down to one round trip. If a _new_ hot, latency-sensitive path ever needs both a DB lookup and rate limiting together, follow that same "combine into one `SECURITY DEFINER` function that calls `check_rate_limit()` internally" pattern rather than two sequential calls from app code.
- **Combined redirect resolution (Module 3.13, don't regress)**: `resolveDynamicQrRedirect(slug, rateLimit?)` (`src/server/services/redirect-resolution.ts`) calls `resolve_qr_redirect_checked` — one Supabase round trip that both resolves the slug _and_ enforces the rate limit, returning a `rate_limited: true` row (with `destination_url`/`status` both `null`) when the caller is over the limit rather than ever leaking the real destination. The `RedirectResolution` type has a fourth `"rate_limited"` status alongside `"ok"`/`"not_found"`/`"inactive"` — any new code that pattern-matches on this type needs to handle all four, not just the original three. The old `resolve_qr_redirect` function (Module 3.6) still exists in the database, unused — don't resurrect it as a "simpler" alternative without re-reading why it was replaced (it would silently reintroduce the two-round-trip latency regression).
- **Security headers / CSP (Module 3.12)**: `next.config.ts`'s `headers()` — if a new external domain is ever needed (a new video host, a new upload destination, etc.), it has to be added to the relevant CSP directive there or the browser will silently block it; check the console for `Content-Security-Policy` / `Refused to` errors first if something loads in dev but "does nothing" (a common CSP symptom). `'unsafe-eval'` on `script-src` is dev-only (`process.env.NODE_ENV === "development"`) — verified live in both modes, don't remove the conditional thinking it's dead code. `img-src` intentionally allows any `https:` origin (Social QR's pasted avatar URLs) — don't tighten it without checking that feature first.
- **Duplicating a Storage-backed QR (Module 3.11, don't regress)**: `duplicateQrAssets()` (`src/lib/qr/asset-sync.ts`) is the only thing that should ever run after inserting a duplicate row for a `needsStorage` type — it copies the actual Storage object (`storage.copy()`) to a new path and gives the duplicate its own `qr_assets` row, then `duplicateQrCode` (`src/lib/qr/actions.ts`) persists the rewritten `payload_data` in a follow-up `.update()`. Never let a duplicate's `payload_data` keep pointing at the _original's_ Storage path — that was the real bug this module fixed (deleting the original would silently break the duplicate). If a new Storage-backed QR type is ever added, its path-rewriting case needs adding to `remapAssetPaths()` in the same file, or duplicating that type will silently skip asset-copying (falls through to the `default: return content` case, leaving the shared-ownership hazard back in place for that one type).
- **QR rendering (Modules 3.2–3.4, all complete)**: `src/lib/qr/render.ts` — `buildQrPayload()` (validate content against the type's Zod schema, then build), `slugifyForFilename()` (now the complete filename policy — Unicode-normalized, diacritics stripped, length-capped), plus the plain `renderQrSvg()`/`renderQrPngDataUrl()` kept only as Module 3.3's error fallback (don't call these directly from new UI — use the styled versions). `src/lib/qr/matrix.ts` (raw module matrix + finder-region geometry) and `src/lib/qr/styled-svg.ts` (`renderStyledQrSvg()`/`renderStyledQrPngDataUrl(payload, design, targetWidth)` — the real, fully-styled renderer everything should call; `targetWidth` is how the 512/1024/2048px presets work) are the current single sources of truth for turning content into a rendered QR. `src/lib/qr/reliability.ts` holds the contrast/logo-size/EC-level/quiet-zone rules — reuse these, don't reimplement. `src/lib/qr/logo.ts`'s `readLogoFile()` is the only place that should touch logo file input handling. **Module 3.5 note**: this whole pipeline is what "regenerate visuals from saved config" means — never store a rendered image in Postgres, store `design_config`/payload and call `renderStyledQrSvg`/`renderStyledQrPngDataUrl` again whenever a saved QR needs to be shown or downloaded.
